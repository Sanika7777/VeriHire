# Deploying VeriHire

Target architecture (CLAUDE.md §3): **Vercel** (web) + **Render** (api +
worker) + **Neon** (Postgres) + **Upstash** (Redis). Every step below is a
browser/dashboard action — nothing here needs a CLI installed locally.

**Cost note, upfront:** Vercel, Neon, and Upstash all have permanently free
tiers sufficient for this app. Render's web service has a free tier too
(it sleeps after 15 minutes idle and takes ~30s to wake up on the next
request). The **background worker has no free tier on Render** — it's
required to actually compute Trust Scores (verification is async) and
costs **~$7/month minimum**. There's no way around that cost on Render;
Fly.io is the CLAUDE.md-listed alternative if you'd rather evaluate its
pricing instead, but it isn't set up in this repo yet.

## 1. Neon — Postgres

1. [neon.tech](https://neon.tech) → sign up (GitHub login is fastest) → New Project.
2. Once created, copy the **connection string** shown on the dashboard. It
   looks like:
   `postgresql://user:password@ep-xxxx.region.aws.neon.tech/dbname?sslmode=require`
3. Rewrite the scheme from `postgresql://` to `postgresql+asyncpg://` (the
   app uses the async driver) — keep the rest, including `?sslmode=require`,
   exactly as Neon gave it. The app already knows how to translate that
   into what asyncpg needs (`apps/api/app/db/session.py`).
4. Keep this final URL handy for step 3.

pg_trgm and pgvector are both created automatically by the first migration
(`alembic upgrade head`) — no manual `CREATE EXTENSION` needed.

## 2. Upstash — Redis

1. [upstash.com](https://upstash.com) → sign up → Create Database (Regional, pick a region close to Render's).
2. On the database page, copy the **`rediss://` connection string** (TLS,
   not the plain `redis://` one) from the "Connect" panel.
3. Keep it handy for step 3.

## 3. Render — API + worker

1. [render.com](https://render.com) → sign up → **New → Blueprint**.
2. Connect your GitHub account and pick the `VeriHire` repo. Render detects
   `render.yaml` at the repo root automatically and shows two services:
   `verihire-api` (web) and `verihire-worker` (background worker, **paid**
   — see cost note above).
3. Before clicking deploy, Render prompts for every env var marked
   `sync: false` in `render.yaml`. Fill in:
   - `DATABASE_URL` — the Neon URL from step 1, on **both** services.
   - `REDIS_URL` — the Upstash URL from step 2, on **both** services.
   - `CORS_ORIGINS` / `FRONTEND_URL` — you don't have the Vercel URL yet.
     Enter a placeholder (e.g. `["http://localhost:3000"]`) for now; you'll
     fix this in step 5.
   - Leave `GOOGLE_OAUTH_*`, `RESEND_API_KEY`, `SENTRY_DSN`,
     `SAFE_BROWSING_API_KEY` blank unless you have real values — every one
     degrades gracefully when unset (`docs/limitations.md`).
   - `JWT_SECRET` is auto-generated by Render — don't fill it in.
4. Deploy. Render builds `apps/api/Dockerfile`, runs
   `uv run alembic upgrade head` as a pre-deploy step (creates the schema),
   then starts `verihire-api`. Watch the logs; first build takes a few
   minutes.
5. Once live, copy `verihire-api`'s public URL
   (`https://verihire-api-xxxx.onrender.com`) — you need it for Vercel next.

## 4. Vercel — web

1. [vercel.com](https://vercel.com) → sign up → **Add New → Project** → import
   the same GitHub repo.
2. In the import screen, set **Root Directory** to `apps/web` (Vercel
   auto-detects Next.js once you do).
3. Add environment variables:
   - `NEXT_PUBLIC_API_URL` = the Render API URL from step 3.5.
   - `NEXT_PUBLIC_SITE_URL` = leave blank for now; Vercel gives you the
     final URL after the first deploy, then come back and set it (and
     redeploy) once you know it.
4. Deploy. Copy the resulting URL
   (`https://verihire-xxxx.vercel.app`, or your custom domain if you add
   one).

## 5. Close the loop — point Render's CORS at the real Vercel URL

1. Back in Render, open `verihire-api` → Environment.
2. Set `CORS_ORIGINS` = `["https://verihire-xxxx.vercel.app"]` (your real
   Vercel URL, exact scheme+host, no trailing slash).
3. Set `FRONTEND_URL` = `https://verihire-xxxx.vercel.app`.
4. Save — Render redeploys automatically.
5. In Vercel, set `NEXT_PUBLIC_SITE_URL` to the same URL and redeploy.

## 6. Seed data (optional, for a populated demo)

From your machine, with `DATABASE_URL` temporarily pointed at the Neon
connection string:

```bash
cd apps/api
DATABASE_URL="postgresql+asyncpg://...neon-url.../db?sslmode=require" \
  uv run python -m app.db.seed
```

This loads the realistic seed dataset and the 8 demo "story" entities
(`docs/demo-script.md`). Safe to run once against a fresh database; running
it again adds a second copy of everything rather than erroring, since it
doesn't truncate first.

**Seeding creates `admin@verihire.app` / `AdminPassword123!` and
`moderator@verihire.app` / `ModeratorPassword123!`** — real, documented,
publicly-known credentials with admin/moderator roles. Fine for a private
demo. If this instance gets real internet traffic, change both passwords
before anyone else can find them — there's no self-service "forgot
password" path that works without `RESEND_API_KEY` configured (without it,
reset emails try localhost SMTP and silently fail), and no in-app way to
promote a user to admin, so the fastest fix is a one-off script against
the same production `DATABASE_URL`:

```bash
cd apps/api
DATABASE_URL="postgresql+asyncpg://...neon-url.../db?sslmode=require" uv run python -c "
import asyncio
from sqlalchemy import select
from app.core.security import hash_password
from app.db.session import async_session_factory
from app.modules.users.models import User

async def main():
    async with async_session_factory() as session:
        user = (await session.execute(select(User).where(User.email == 'admin@verihire.app'))).scalar_one()
        user.password_hash = hash_password('a real password of your choosing')
        await session.commit()

asyncio.run(main())
"
```

Repeat for `moderator@verihire.app`, or just delete both rows and register
fresh accounts through the normal signup flow instead (registration
doesn't require a working email — email verification is separate from
being able to log in).

## Verify

- `curl https://<your-render-api>.onrender.com/health` → `200`
- `curl https://<your-render-api>.onrender.com/ready` → `200`,
  `database: true`, `redis: true`
- Open the Vercel URL, register an account, verify a company end-to-end —
  confirms CORS, cookies, and the worker are all wired correctly.
- Log out and back in, then refresh the page while logged in — this is the
  specific check for the cross-site cookie fix (`SameSite=None`): if it
  silently logs you out on refresh, `CORS_ORIGINS`/the cookie domain isn't
  set correctly yet.

## Known gap worth knowing before a real launch

There's no CSRF token on the cookie-authenticated routes (CLAUDE.md §9
calls for one; it was never implemented). The refresh cookie is
`httponly`, and the only actions it gates are token refresh and logout —
both low-consequence if triggered cross-site — so this isn't blocking for
a demo/soft launch, but should be addressed before real user accounts and
money are involved.
